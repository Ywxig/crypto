## Введение

Четыре рассматриваемые темы образуют логическую цепочку:

1. **Поле Галуа** задаёт структуру, в которой выполняются вычисления.
2. **Модулярное возведение в степень** — базовая операция.
3. **Обратный элемент по модулю** — «деление» в конечном поле.
4. **Дискретный логарифм** — обратная к возведению в степень задача; на её сложности держится стойкость DH, Эль-Гамаля, ECC.

Цель работы: реализовать несколько алгоритмов для каждой темы, проверить их на примерах из методички и сравнить по **времени выполнения** и **целесообразности использования**.

В таблицах ниже «время» — асимптотическая оценка плюс число модулярных умножений, которое я посчитал на тестовых данных. Реальные замеры в миллисекундах зависят от машины и компилятора, их нужно вставить из собственного запуска (см. раздел «Замеры»).

## 1. Поле Галуа GF(2⁸) (задание 1)

Рассматриваются три способа умножения в GF(2⁸) с неприводимым многочленом x⁸+x⁴+x³+x+1 (0x11B), как в AES, и способ нахождения обратного элемента.

### 1.1 Крестьянское умножение (сдвиги и XOR) — п. 3.1.1

Умножение «в столбик» по битам множителя: сложение — XOR, умножение на x — сдвиг влево с редукцией по 0x1B при выходе за 8 бит.

| Плюсы | Минусы |
|---|---|
| Только сдвиги и XOR — очень быстро и дёшево в аппаратуре | O(n) шагов по числу бит поля, плохо масштабируется на большие поля |
| Не нужны деление и дополнительная память | Даёт только произведение, обратный элемент напрямую не находит |
| Легко сделать за постоянное время (цикл всегда 8 итераций) | |

### 1.2 Расширенный алгоритм Евклида для многочленов — п. 3.1.2

Евклид над многочленами с делением в смысле XOR; коэффициент Безу при остатке 1 — обратный элемент.

| Плюсы | Минусы |
|---|---|
| Работает для любого неприводимого многочлена и любого размера поля | Сложнее в реализации: нужны отдельные деление и умножение многочленов |
| Универсальный способ получить обратный элемент | Для малого фиксированного поля (GF(2⁸)) медленнее таблиц |

### 1.3 Таблицы логарифмов и антилогарифмов — п. 3.1.3

Умножение сводится к сложению индексов: a·b = g^((log a + log b) mod 255).

| Плюсы | Минусы |
|---|---|
| После предвычисления умножение за O(1) | Нужна память под таблицы и время на их построение |
| Идея проста: умножение превращается в сложение | Не применимо для больших GF(2ⁿ): размер таблицы растёт как 2ⁿ |
| | Нужен именно **образующий** элемент g |

**Важное замечание.** Для многочлена 0x11B элемент `0x02` **не** является образующим: его порядок равен 51, а не 255. Таблицы нужно строить на `g = 0x03`. С `g = 0x03` таблица содержит все 255 ненулевых элементов.

### 1.4 Проверка корректности (п. 3.1.4)

Пример из FIPS-197: **0x57 · 0x83 = 0xC1**.

| Метод | Результат | Совпадение |
|---|---|---|
| Крестьянское умножение | 0xC1 | да |
| Таблицы log/antilog (g = 0x03) | 0xC1 | да |
| Расширенный Евклид (через обратный элемент, например 0x53⁻¹ = 0xCA) | 0xCA | да |

Дополнительно умножение по таблицам было сверено с крестьянским на всех 256·256 парах — расхождений нет.

### 1.5 Сравнение и целесообразность

| Критерий | Крестьянское | Евклид для многочленов | Таблицы |
|---|---|---|---|
| Время одной операции | O(n), 8 шагов | O(n²) по битовым операциям, много шагов | O(1) |
| Подготовка | нет | нет | O(2ⁿ) |
| Память | O(1) | O(1) | O(2ⁿ) |
| Постоянное время | да (легко) | нет | нет (обращение к таблице по секретному индексу — риск кэш-атак) |
| Что вычисляет | произведение | обратный элемент | произведение, обратный через таблицу |

**Вывод.** Для программной реализации AES при большом потоке данных быстрее всего таблицы (но они уязвимы к атакам по кэшу). Для аппаратной и встраиваемой реализации и там, где важна защита от атак по времени, лучше крестьянское умножение. Расширенный Евклид нужен, когда поле большое или многочлен произвольный, либо когда таблицы строить нецелесообразно.

## 2. Модулярное возведение в степень (задание 2)

Вычисляется bᵉ mod m без построения огромного bᵉ. Реализованы четыре метода (3.2.1–3.2.4); эталонная программа из 3.5.1 фактически реализует вариант справа налево.

### 2.1 Двоичный метод справа налево (RTL) — п. 3.2.1

| Плюсы | Минусы |
|---|---|
| Прост в реализации и анализе | Ветвление `if` по биту показателя — утечка секретного показателя по времени |
| O(log e) умножений | Не постоянное время |
| Биты обрабатываются «на лету», показатель не нужно знать заранее | |

### 2.2 Двоичный метод слева направо (LTR) — п. 3.2.2

| Плюсы | Минусы |
|---|---|
| Естественен для ручного расчёта (так построены таблицы в 3.5.1) | Нужно знать весь показатель заранее |
| Удобно комбинировать с оптимизациями (скользящее окно) | Не постоянное время |
| Та же сложность O(log e), что и у RTL | |

### 2.3 Лестница Монтгомери — п. 3.2.3

| Плюсы | Минусы |
|---|---|
| На каждом шаге одни и те же операции независимо от бита — устойчива к атакам по времени и побочным каналам | Больше умножений, чем в простых методах (всегда 2 на бит) |
| Фактический стандарт для RSA/ECC | Сложнее проверять на корректность |

### 2.4 Скользящее окно — п. 3.2.4

| Плюсы | Минусы |
|---|---|
| Уменьшает число умножений на длинных показателях | Предвычисление малых нечётных степеней и память под них |
| Выгодно при многократном использовании одного основания | Сложнее реализация |
| | Длина и положение окон выдают информацию — не постоянное время |

### 2.5 Проверка корректности

Все четыре метода проверены на примерах из 3.5.1 и классическом примере 4¹³ mod 497.

| Пример | Ожидаемый результат | RTL | LTR | Монтгомери | Окно |
|---|---|---|---|---|---|
| 4¹³ mod 497 | 445 | 445 | 445 | 445 | 445 |
| 15⁴⁹⁴⁷ mod 31 | 23 | 23 | 23 | 23 | 23 |
| 7181²⁹⁵³ mod 9286 | 9247 | 9247 | 9247 | 9247 | 9247 |
| 5617¹²³⁴ mod 9627 | 3979 | 3979 | 3979 | 3979 | 3979 |

### 2.6 Число модулярных умножений

| Тест | RTL | LTR | Монтгомери | Окно (k = 4) |
|---|---|---|---|---|
| 4¹³ mod 497 (4 бита) | 7 | 7 | 8 | 13 |
| 15⁴⁹⁴⁷ mod 31 (13 бит) | 20 | 20 | 26 | 25 |
| 7181²⁹⁵³ mod 9286 (12 бит) | 18 | 18 | 24 | 23 |
| 5617¹²³⁴ mod 9627 (11 бит) | 16 | 16 | 22 | 22 |
| случайный 520-битный показатель, модуль 2⁵²¹−1 | 797 | 797 | 1040 | 636 |

Для коротких показателей окно **проигрывает** из-за затрат на предвычисления, и только на длинных (сотни бит) даёт выигрыш около 20% относительно простых методов. Лестница Монтгомери всегда дороже примерно на 30% — это плата за постоянное время.

### 2.7 Сравнение и целесообразность

| Метод | Время | Постоянное время | Когда применять |
|---|---|---|---|
| RTL | O(log e) | нет | учебные задачи, открытые показатели (шифрование RSA с e = 65537) |
| LTR | O(log e) | нет | основа для оконных методов, ручной расчёт |
| Лестница Монтгомери | O(log e), 2 умножения на бит | да | секретные показатели (подпись/расшифровка RSA, DH, ECC) |
| Скользящее окно | меньше умножений, но есть предвычисление | нет | длинные показатели и повторное использование основания |

**Вывод.** Если показатель публичный — достаточно RTL/LTR. Если секретный — нужна лестница Монтгомери (либо окно с защитой от утечек). Скользящее окно оправдано только на больших показателях.

**Замечание к эталонному коду 3.5.1.** Тип `long long` безопасен лишь при n < ~3·10⁹ (иначе произведение `a*a` переполняется); для реальных ключей нужна длинная арифметика (GMP и т. п.).

## 3. Обратный элемент по модулю (задание 3)

Нужно найти x: a·x ≡ 1 (mod m). Решение существует тогда и только тогда, когда gcd(a, m) = 1. Реализованы три метода (3.3.1–3.3.3).

### 3.1 Расширенный алгоритм Евклида — п. 3.3.1

| Плюсы | Минусы |
|---|---|
| Работает для любого модуля, не только простого | Переменное число шагов и деления — не постоянное время |
| Быстрый: O(log min(a, m)) шагов | Хуже распараллеливается, чем методы на основе возведения в степень |
| Сам сообщает об отсутствии обратного (gcd ≠ 1) | |

### 3.2 Метод Ферма — п. 3.3.2

a⁻¹ ≡ a^(p−2) mod p, использует модулярное возведение в степень.

| Плюсы | Минусы |
|---|---|
| Очень прост, если уже есть mod_pow | Работает **только** для простого модуля |
| Постоянное время при использовании лестницы Монтгомери | Дороже Евклида: O(log p) полных модулярных умножений |
| | При составном модуле даёт неверный результат без предупреждения |

### 3.3 Двоичный алгоритм Евклида — п. 3.3.3

| Плюсы | Минусы |
|---|---|
| Нет деления: только сдвиги, сложение, вычитание | Требует **нечётного** модуля m |
| Очень быстр в аппаратной и встраиваемой реализации | Много частных случаев и ветвлений, легко ошибиться |
| | Трудно сделать за постоянное время |

### 3.4 Проверка корректности

| Пример | Ожидаемо | Евклид | Ферма | Двоичный Евклид |
|---|---|---|---|---|
| 3⁻¹ mod 11 (п. 3.3.4) | 4 | 4 | 4 | 4 |
| 7⁻¹ mod 11 | 8 | 8 | 8 | 8 |
| 1182⁻¹ mod 578 | не существует (gcd = 2) | не существует | неприменим (578 — не простое) | неприменим (578 чётное) |
| 1777⁻¹ mod 2699 | 1853 | 1853 | 1853 (2699 — простое) | 1853 |

Проверка: 7·8 = 56 = 5·11 + 1; 1777·1853 ≡ 1 (mod 2699).

Пример 2 показывает ключевое преимущество Евклида: он единственный из трёх корректно диагностирует отсутствие обратного элемента.

### 3.5 Сравнение и целесообразность

| Критерий | Евклид | Ферма | Двоичный Евклид |
|---|---|---|---|
| Время | O(log m) | O(log p) умножений (дороже) | O(log m), без деления |
| Ограничения на модуль | нет | простой | нечётный |
| Постоянное время | нет | да (с лестницей) | нет |
| Обнаружение отсутствия обратного | да | нет | частично |

**Вывод.** Расширенный Евклид — универсальный выбор по умолчанию. Ферма уместен при простом модуле и требовании постоянного времени. Двоичный Евклид оправдан на «железе» без быстрого деления.

**Замечание к эталонному коду 3.5.2.** Тип `int` переполняется на больших числах (выражение `t0 - q*t`); для больших модулей нужны `long long` или длинная арифметика. Условие проверки `b <= 1` отбрасывает также значение b = 1.

## 4. Дискретный логарифм (задание 4)

Задача: по g, h, p найти x, для которого gˣ ≡ h (mod p). Эффективного алгоритма для общего случая не известно, на этом держится безопасность DH, Эль-Гамаля, ECC. Реализованы пять методов (3.4.1–3.4.5).

### 4.1 Полный перебор — п. 3.4.1

| Плюсы | Минусы |
|---|---|
| Тривиален, не требует памяти | O(p) — неприменим при p в сотни бит |

### 4.2 «Шаг младенца — шаг великана» (BSGS) — п. 3.4.2

| Плюсы | Минусы |
|---|---|
| Детерминированный, O(√p) по времени | O(√p) памяти — для очень больших p непрактичен |
| Прост концептуально («встреча посередине») | Нужен обратный элемент (расширенный Евклид) |

### 4.3 Ро-алгоритм Полларда — п. 3.4.3

| Плюсы | Минусы |
|---|---|
| O(√p) времени, как у BSGS, но O(1) памяти | Вероятностный, время не гарантировано |
| Подходит, когда память ограничена | Финальное решение сравнения может не удаться — нужен перезапуск с другими параметрами |
| | Корректно работает при простом порядке группы |

### 4.4 Алгоритм Полига — Хеллмана — п. 3.4.4

| Плюсы | Минусы |
|---|---|
| Очень эффективен при «гладком» порядке группы | Бесполезен, если порядок содержит большой простой делитель |
| Сводит задачу к малым подзадачам (с использованием КТО) | Сам по себе опирается на BSGS или ро-метод для подгрупп |

Практический смысл — именно поэтому в криптографии выбирают группы **большого простого порядка**.

### 4.5 Метод исчисления индексов — п. 3.4.5

| Плюсы | Минусы |
|---|---|
| Субэкспоненциальная сложность, самый быстрый для мультипликативных групп по модулю p | Сложная реализация (большие линейные системы по модулю p−1) |
| Объясняет, почему для RSA/DH нужны ключи 2048+ бит | Нет эффективного аналога для эллиптических кривых — поэтому ECC обходится ключами меньшей длины |

### 4.6 Проверка корректности

| Пример | Ожидаемо | Результат |
|---|---|---|
| 31ˣ ≡ 3 (mod 29), т. е. 2ˣ ≡ 3 | x = 5 | 5 |
| 2ˣ ≡ 22 (mod 29), BSGS (п. 3.4.6) | x = 26 | 26 (i = 4, j = 2; проверка: 2²⁶ ≡ 22) |

Для p = 29 порядок группы равен 28 = 2²·7 — гладкий, поэтому Полиг — Хеллман решает задачу мгновенно; ро-алгоритм Полларда для составного порядка требует аккуратной обработки сравнения. Метод исчисления индексов на столь малом модуле показателен лишь учебно (факторная база из нескольких малых простых).

Дополнительно BSGS и полный перебор сверены на p = 1 000 003 и p = 10 000 019: результаты совпали.

### 4.7 Сравнение и целесообразность

| Метод | Время | Память | Применимость |
|---|---|---|---|
| Полный перебор | O(p) | O(1) | только учебные малые p |
| BSGS | O(√p) | O(√p) | средние p, когда память есть |
| Ро-Поллард | O(√p), вероятностно | O(1) | большие p при ограниченной памяти |
| Полиг — Хеллман | зависит от наибольшего простого делителя порядка | малая | гладкий порядок группы |
| Исчисление индексов | субэкспоненциально | большая | реальные атаки на DH/RSA-подобные группы по модулю p |

**Вывод.** Для обучения и малых чисел подходят перебор и BSGS. Если память критична — ро-метод. Если порядок группы гладкий — Полиг — Хеллман ломает систему вне зависимости от размера p. Для больших простых модулей самой опасной является атака исчисления индексов, поэтому нужны ключи 2048+ бит (для ECC — достаточно 256 бит).

**Замечание к эталонному коду 3.5.3.** Метод перебора ограничен LIMIT = 32000 и не находит решения для больших p; в сообщении об ошибке «No solution found» нельзя отличить «решения нет» от «решение за пределом».

## Общие выводы

1. Не существует «лучшего» алгоритма вообще: выбор определяется размером данных, ограничениями по памяти и требованием **постоянного времени** (защита от атак по сторонним каналам).
2. Для секретных данных важнее всего не скорость, а отсутствие зависимости времени от значения секрета: лестница Монтгомери, Ферма с лестницей, крестьянское умножение.
3. Для публичных данных выгодны быстрые методы с ветвлениями: RTL/LTR, окно, расширенный Евклид, таблицы.
4. Безопасность криптосистем с открытым ключом основана на асимметрии: возведение в степень вычисляется за O(log e), а дискретный логарифм — в лучшем случае субэкспоненциально.
5. Эталонные программы методички (тип `int`/`long long`) пригодны только для небольших чисел; в реальных приложениях нужна длинная арифметика.
